3Key Design Decisions

3.1Cart items vs. order-item snapshots

cart_items stores only book_id and quantity — no price. The live price is read from books.price each time the cart is displayed or validated, so the basket always reflects the current catalogue price.

order_items captures book_title, unit_price, and subtotal at checkout. These values are immutable after the order is created, so later catalogue price changes never alter past receipts. The book_id FK is retained so "Buy Again" and Recommendations can navigate back to the live record.

Columns marked [snap] in the ER diagram are the frozen snapshot fields.
3.2Delivery address handling

user_addresses is a reusable address book. One row may be flagged is_default.

At checkout, the chosen address fields (recipient_name, phone, street, city, state, postal_code, country) are copied inline into the orders row. There is no FK from orders back to user_addresses.

Snapshot design: editing or deleting a saved address never alters a historical order confirmation.
3.3Reward-points fields

users.reward_points is the running balance — incremented on successful payment, decremented on cancellation.

orders records points_redeemed (applied at checkout) and points_earned (credited on successful payment).

Earning basis is the subtotal, not total_amount:

pointsToCredit = floor(order.subtotal) // 1 point per whole dollar of subtotal // tax, shipping, and redemption discounts are excluded

Cancellation reversal (no external ledger needed):

new_balance = max(0, current_balance + points_redeemed − points_earned)
3.4Inventory (stock_quantity)

books.stock_quantity is decremented only on successful payment — not at checkout.

There is no reservation step. Stock is neither decremented nor locked when an order is created or when a payment attempt fails. Two customers can both reach the payment screen for the last copy of a book.

PaymentService performs a fresh availability check immediately before decrementing. If stock has run out, InsufficientStockException is thrown.

The optimistic-lock version column on books prevents a double-decrement race when two concurrent successful payment requests target the same book simultaneously.

On cancellation: stock is restored by incrementing stock_quantity by the sum of order_items.quantity.
3.5Multiple payment attempts per order

payments.order_id is a plain FK with no UNIQUE constraint, so one order can accumulate multiple payment rows — for example, a FAILED attempt followed by a successful retry.

Idempotency is enforced by service logic, not by the unique constraint: when POST /orders/{id}/payments is called on an already-PAID order, PaymentService queries for an existing SUCCESS record and returns it unchanged — no new row is created.

The payment_reference UNIQUE constraint serves a narrower purpose: guaranteeing a collision-safe reference for each individual attempt, including failed ones.

⚑ This is the key cardinality: Order 1 → many Payments. The implementation plan's original diagram incorrectly showed 1:1 — corrected to 1:N.
3.6One cart per user & cart clearing

carts.user_id carries a UNIQUE constraint — one cart per customer, enforced at the database level. The cart row is created on registration and is never deleted.

When the cart is "cleared" after successful payment, PaymentService calls cart.getItems().clear() and saves via JPA. Because Cart declares @OneToMany(cascade = ALL, orphanRemoval = true), Hibernate issues DELETE statements for the orphaned cart_items rows.

This is JPA orphan-removal, not the SQL ON DELETE CASCADE on the FK. The DDL cascade fires only if the carts row itself were deleted directly in the database — which the application never does.

4Schema Constraints Summary

Type Table / Column(s) Purpose
UNIQUE users.username, users.email Prevents duplicate accounts
UNIQUE categories.slug URL-safe category identifier
UNIQUE publishers.name No duplicate publisher records
UNIQUE books.isbn One catalogue entry per ISBN
UNIQUE carts.user_id One active cart per customer
UNIQUE cart_items(cart_id, book_id) No duplicate book title in the same cart
UNIQUE orders.order_number Human-readable order reference
UNIQUE payments.payment_reference Collision-safe reference per attempt (not the idempotency guard — that is service logic)
CHECK cart_items.quantity > 0 Cart item quantity must be positive
CHECK order_items.quantity > 0 Order line item quantity must be positive
ON DELETE CASCADE user_addresses.user_id → users Addresses removed when account is deleted
ON DELETE CASCADE cart_items.cart_id → carts DDL safety net only — normal clearing uses JPA orphan-removal, not this cascade
ON DELETE CASCADE order_items.order_id → orders Order line items removed with the order row
Optimistic lock books.version (BIGINT) Prevents double-decrement race on concurrent successful payment requests for the same book
